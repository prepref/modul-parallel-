## Bot Aggregator (Telegram → Redis)

Сервис поднимает **несколько Telegram-ботов** (по токенам из переменных окружения), делает **long polling** (`getUpdates`) и **публикует каждое входящее обновление в Redis-очередь** (Redis List). Дальше любые ваши потребители (воркеры/микросервисы) могут забирать события из Redis и обрабатывать их.

### Что умеет

- **Мультибот**: запускает несколько ботов одновременно (`BOT_1`, `BOT_2`, ...).
- **Long polling** Telegram API: без вебхуков.
- **Rate limiting**: глобальный лимит на контейнер и отдельный лимит на каждого бота.
- **Очередь в Redis**: события сериализуются в JSON и кладутся в Redis List (`RPUSH`).
- **Логи**: в stdout и в файл с ротацией.

## Быстрый старт (Docker Compose — рекомендуемый способ)

### 1) Создайте `.env` в корне проекта

Файл читается автоматически при запуске контейнера (см. `docker-compose.yml`).

Пример минимальной конфигурации:

```dotenv
# Один или несколько ботов. Формат: <messenger>:<token>
# Для Telegram: telegram:<TELEGRAM_BOT_TOKEN>
BOT_1=telegram:123456789:AAExampleTokenGoesHere
# BOT_2=telegram:...

# Опционально: уровень логирования
LOG_LEVEL=INFO

# Опционально: имя Redis-очереди
REDIS_QUEUE=event_queue

# Опционально: если хотите подключаться к внешнему Redis вместо compose-сервиса
# REDIS_URL=redis://host:6379
```

Важно:
- `BOT_*` парсится как `messenger:token`, при этом **токен может содержать двоеточия** (у Telegram так и есть). Разделение делается только по **первому** `:`.
- Сейчас поддерживается только `telegram`.

### 2) Запуск

```bash
docker compose up --build
```

Проверка логов:

- Логи контейнера:

```bash
docker logs -f bot-aggregator
```

- Файл логов (монтируется в `./logs`): `logs/bot_aggregator.log`

## Конфигурация (переменные окружения)

### Боты

- **`BOT_1`, `BOT_2`, ...**
  - **Назначение**: список ботов, которые нужно запустить.
  - **Формат**: `<messenger>:<token>`
  - **Пример**: `BOT_1=telegram:123456789:AA...`

Если `BOT_*` не задан ни один — сервис завершится с ошибкой и подсказкой.

### Redis

- **`REDIS_URL`** (по умолчанию формируется из `REDIS_HOST`/`REDIS_PORT`)
  - **По умолчанию**: `redis://redis:6379` (в Compose это имя сервиса `redis`)
  - Для локального Redis обычно удобно `redis://localhost:6379`

- **`REDIS_HOST`** (по умолчанию `redis`)
- **`REDIS_PORT`** (по умолчанию `6379`)

- **`REDIS_QUEUE`**
  - **Назначение**: имя Redis List (очередь событий)
  - **По умолчанию**: `event_queue`

Поведение подключения:
- при старте сервис делает несколько попыток подключения (до 10) с задержкой.

### Логи

- **`LOG_LEVEL`**
  - **По умолчанию**: `INFO`
  - Примеры: `DEBUG`, `INFO`, `WARNING`, `ERROR`

Логи пишутся:
- в stdout
- в файл `/app/logs/bot_aggregator.log` с ротацией (10MB, до 5 файлов)

## Архитектура и поток данных

### Основной поток

1. `app/main.py` читает `.env` и ищет все переменные `BOT_*`.
2. Для каждого `BOT_*` создаётся адаптер (сейчас `TelegramAdapter`) и запускается polling.
3. Каждый `Update` Telegram сериализуется в dict и отправляется в Redis List через `RPUSH`.

### Модули

- `app/main.py` — точка входа, запуск задач для каждого бота.
- `app/config.py` — загрузка `.env` и парсинг `BOT_*`.
- `app/adapters/telegram.py` — long polling Telegram и публикация событий.
- `app/redis/redis_queue.py` — подключение к Redis и публикация в очередь.
- `app/core/rate_limit.py` — rate limiting для запросов к Telegram.
- `app/core/logger.py` — настройка логирования.

## Rate limiting (ограничения запросов)

Применяется к вызову `get_updates`:
- **Глобально**: до **20 запросов/сек** на весь процесс (контейнер) — запас относительно лимитов Telegram.
- **На бота**: до **1 запроса/сек** на каждый токен.

## Формат события в Redis

Событие кладётся в Redis List как **UTF-8 JSON** (bytes). Общая структура:

```json
{
  "messenger": "telegram",
  "token": "<полный токен бота>",
  "data": { "update_id": 123, "message": { /* ... */ } }
}
```

Примечание по безопасности:
- В payload сейчас передаётся **полный токен**. Если очередь/логи доступны посторонним — это риск. Обычно токен не нужен потребителям, и его стоит исключить или заменить на безопасный идентификатор бота.

## Как потреблять очередь (потребитель/воркер)

Паблишер добавляет элементы командой `RPUSH`, то есть события лежат в списке в порядке поступления (FIFO). Типичный потребитель делает:

- **Блокирующее чтение** (рекомендуется для воркера):

```bash
redis-cli -h localhost -p 6379 BLPOP event_queue 0
```

- **Неблокирующее чтение**:

```bash
redis-cli -h localhost -p 6379 LPOP event_queue
```

Замечание по надёжности:
- С текущей схемой (List + `LPOP/BLPOP`) удаление происходит в момент получения. Если воркер упал во время обработки, событие уже удалено. Для «как минимум один раз» обычно используют паттерн `RPOPLPUSH`/`BRPOPLPUSH` (в processing-list) и явное подтверждение (ACK) после успешной обработки.

## Типовые проблемы и решения

- **«Не найдено ни одного бота в конфигурации»**
  - Проверьте, что создан `.env` в корне и в нём есть `BOT_1=telegram:<token>`.

- **Не удаётся подключиться к Redis**
  - При запуске через Compose убедитесь, что `docker compose up` поднял сервис `redis`.
  - При локальном запуске установите `REDIS_URL=redis://localhost:6379`.

- **Telegram API ошибки / бот молчит**
  - Проверьте токен.
  - Сервис пытается удалить webhook (на всякий случай) — это нормально.
